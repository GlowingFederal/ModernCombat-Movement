# ModernCombat&Movement
Modern combat mechanics and movement, including swimming and crawling for legacy versions.

Targets: Forge 1.7.10, 1.8.9 and 1.12.2, running Java 8. The reference is vanilla Java Edition 1.21.11, with verified later corrections tracked separately. This is an early development build; [implementation status](docs/STATUS.md) and [combat kit coverage](docs/COMBAT-KIT.md) distinguish implemented behavior from planned parity.

Install matching mod versions on the client and server. Forge 1.7.10 requires UniMixins 0.3.1 and Modern Regen 1.0.2.2 or newer; 1.12.2 requires MixinBooter 11.18. The 1.8.9 distribution includes its Mixin runtime. UAB is optional: its existing item registrations are reused through explicit adapters. [LOTR Legacy compatibility](docs/LOTR-COMPATIBILITY.md) preserves LOTR combat by default. Unknown modded weapons and projectiles retain their own behavior unless an integration explicitly registers them.

Build all targets with `python scripts/build.py all`, or one target with `python scripts/build.py build 1.7.10` (substitute another supported version). PowerShell and shell entry points are also in `scripts`. Builds require Python 3, JDK 25 for 1.7.10 and JDK 21 for 1.8.9/1.12.2; packaged bytecode remains Java 8. Set `JAVA25_HOME` and `JAVA21_HOME` if the launchers cannot find those JDKs. `version.properties` manages the version and next build number; standard distributable JARs go to `build/release`.

See the [mechanics parity matrix](docs/PARITY.md) and [technical architecture and integration API](docs/ARCHITECTURE.md) for source references, ownership and development conventions. Configuration uses Forge's native files, with separate combat, movement, swimming, crawling, equipment, offhand, shield, projectile and flight controls. Existing equipment and flight settings migrate automatically. Potion and enchantment IDs must match between client and server; mismatches produce a connection diagnostic.

The Mods configuration screen exposes hold/toggle sprint and sneak, the creative-flight boost slider, attack-indicator placement and item cooldown overlays. Hold controls remain the default. Toggles clear when a screen, lost focus or player lifecycle change interrupts play. Better Sprinting takes priority over MCM's input and flight-boost handling when installed. Combatives remains optional and owns ordinary swimming, crawling, geometry and camera behavior when both mods are present.

Creative-flight boost is off by default. Its additional multiplier ranges from 1 to 5 and requires the server's permission; the server can lower `Flight.maximumCreativeFlightMultiplier` to 1 to disable it. It applies only to creative sprint flight and restores the previous capability speed afterward. Attack indicators can use the crosshair, hotbar or be disabled; 1.12 also offers the unchanged native Video Settings choice. Item overlays show the actual reuse restriction, including pearls, wind charges and disabled shields.

On 1.7.10 and 1.8.9, the saved offhand slot follows vanilla's survival and creative inventory placement. Press **F** to swap hands, or hover an eligible container slot and press F to exchange it with the offhand. The key can be rebound in Controls. Supported items use the offhand when the main interaction passes, including native animal feeding, milking, fishing, shields and projectile ammunition. Crossbows accept arrows and fireworks; totems can activate from either hand. Modded items can be stored and rendered, while use may require an explicit integration. See the coverage matrix for remaining development and verification limits.

On legacy targets, keep the existing MCM configuration and `config/legacy-potion-ids.properties` with the modpack and saved worlds. New potion effects receive persistent IDs through the shared allocation file; existing configured effect IDs remain unchanged. Install matching allocation files on clients and servers.

Legacy standalone bows and crossbows accept tipped and spectral arrows, including ammunition held in the offhand. Native 1.12 ammunition and UAB item registrations are reused when available. Standalone recipes, brewing and survival acquisition are outside this project's scope; UAB retains its own recipes and progression.
